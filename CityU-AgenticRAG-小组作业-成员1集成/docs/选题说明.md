## 一、中文版

### 题目

**CityU 学生服务 Agentic RAG 问答系统：面向校园 / 国际学生 / 新生服务 FAQ 的数据库应用**
（副标题：以香港城市大学官网公开信息为语料，构建"采集—清洗—入库—检索—生成"端到端数据库应用）

### Track 选择

**Track 1（数据库应用开发）**。理由：本选题天然覆盖 Track 1 的全部评分点——真实数据建模（关系表 + 向量索引的混合存储）、有意义的查询（结构化过滤 + 语义检索 + 混合排序）、以及数据库工程实践（幂等写入、索引策略、可复现评测）；我们已完成前期可行性研究与采集器原型，具备真实数据源。

### 内容简介

面向香港城市大学的新生与国际学生，把分散在官网 6 个以上部门子站的公开服务信息（**申请、注册、签证、宿舍、学费、奖学金、图书馆、校历** 八大主题）汇聚为**可溯源的问答系统**，解决"信息分散、入口深、时效性强、新生不知去哪查"的真实痛点。

系统分四层：

1. **采集层**：对城大官网与图书馆 LibGuides 等公开来源做**增量、幂等、限速**抓取（请求间隔 2–3 秒，遵守网站条款，仅课程用），已实现可运行爬虫（`src/`）与标准化集成测试。
2. **存储层**：关系数据库保存文档元数据（来源 URL、主题、学年、抓取时间、状态）与清洗后的结构化内容，含 SQL 查询与索引设计（URL 唯一约束保证幂等，按主题/学年建索引）。
3. **检索层**：语料切块后建立**向量索引**（HNSW/FAISS 类近似最近邻），提供"主题过滤 + 语义检索"的混合检索。
4. **生成层**：**Agentic RAG** —— 由路由 Agent 按问题类型分派工具（校历查询 / 费用查询 / 签证流程 / 全文语义检索），支持多跳检索，并以 Self-RAG / CRAG 式自反思与**来源引用**抑制幻觉、保证可核查。

**评测**：构建 FAQ 问答测试集，度量检索命中率、答案忠实度（引用可溯源率）与查询延迟，并与"纯 LLM 无检索""朴素单轮 RAG"两个基线对比。

**目标用户**：本地与非本地新生、国际学生与交换生、招生咨询者、院系前台与课程导师。

### 类似应用（参考与差异）

- **Georgia Tech「Jill Watson」虚拟助教**（Goel & Polepeddi, 2016）：论坛问答自动应答的著名高校案例，但基于规则/分类模型、无引用溯源。
- **高校招生与学生服务问答机器人**（如 Ivy.ai、Mainstay 等商业产品）：多为单轮 FAQ 检索，缺乏 Agentic 多工具路由与可核查引用。
- **城大官方现状**：各部门已有 FAQ（ADMO 招生 FAQ、SRO 分人群宿舍 FAQ、ARRO 规章与重要日期、FO 学费页、SGS 招生手册 PDF），信息权威但**入口分散、跨部门问题需人工串联**。本项目差异点：统一入口 + 按主题分工具的动态检索 + 每条回答附来源 URL 与学年标注。

### 数据库设计要点（Track 1 评分对应）

- 表结构：`documents`（url 唯一、title、source、topic、academic_year、crawled_at）、`chunks`（chunk_id、doc_id、text、embedding）、`crawl_runs`（幂等与增量审计）、`qa_logs`（问答与引用日志）。
- 规范化：元数据满足 3NF；向量列以扩展模块（如 sqlite-vec）或独立 ANN 索引存放，避免破坏关系设计。
- 索引策略：URL / (topic, academic_year) / crawled_at 建立 B-tree 索引；向量列建 HNSW 索引。
- 示例查询：① 列出 2025/26 学年非本地生学费相关文档并按其结构字段排序；② 语义检索"学生签证要多久、需要什么材料"并返回 TOP-k 及其来源 URL。

## 二、English Version

### Title

**An Agentic RAG Question-Answering System for CityU Student Services: A Database Application over Public FAQ Content for Campus, International and New Students**
(Subtitle: An end-to-end "crawl → clean → store → retrieve → generate" database application built on publicly available information from the City University of Hong Kong website)

### Track Selection

**Track 1: Database Application Development.** The topic naturally covers every Track 1 grading criterion — real-world data modeling (a hybrid of relational tables and vector indexing), meaningful queries (structured filtering + semantic retrieval + hybrid ranking), and database engineering practices (idempotent writes, indexing strategy, reproducible evaluation). A feasibility study and a working crawler prototype over live data sources have already been completed.

### Brief Description

Targeting new and international students at City University of Hong Kong, the system consolidates publicly available service information scattered across more than six departmental sub-sites (**admissions, registration, visa, student residence, tuition fees, scholarships, library, academic calendar**) into a **citation-traceable question-answering system**, addressing a genuine pain point: information is fragmented, buried deep, time-sensitive, and hard for newcomers to locate.

The system has four layers:

1. **Ingestion layer**: incremental, idempotent, rate-limited crawling (2–3 s between requests, respecting site terms, coursework use only) of the CityU website and library LibGuides; a runnable crawler (`src/`) with standardized integration tests already exists.
2. **Storage layer**: a relational database stores document metadata (source URL, topic, academic year, crawl time, status) and cleaned structured content, with SQL queries and indexing (a unique constraint on URL enforces idempotency; indexes on topic/academic year).
3. **Retrieval layer**: chunked corpus is indexed with **approximate nearest-neighbour vector indexes** (HNSW/FAISS-style), supporting hybrid "topic filter + semantic search" retrieval.
4. **Generation layer**: **Agentic RAG** — a routing agent dispatches question types to specialized tools (academic-calendar lookup, fee lookup, visa procedure, full-text semantic search), supports multi-hop retrieval, and uses Self-RAG/CRAG-style self-reflection with **source citations** to suppress hallucination and guarantee verifiability.

**Evaluation**: an FAQ QA test set measuring retrieval hit rate, answer faithfulness (citation-traceability rate) and query latency, compared against two baselines: "LLM without retrieval" and "naive single-round RAG".

**Target users**: local and non-local freshmen, international and exchange students, admissions enquirers, departmental front-desk staff and academic advisers.

### Similar Applications (and Our Differentiation)

- **"Jill Watson" virtual teaching assistant at Georgia Tech** (Goel & Polepeddi, 2016): the well-known campus Q&A deployment, yet rule/classifier-based with no citation tracing.
- **Commercial higher-education chatbots** (e.g. Ivy.ai, Mainstay): mostly single-turn FAQ retrieval, without agentic multi-tool routing or verifiable citations.
- **CityU today**: authoritative FAQ content exists per department (ADMO admissions FAQ, SRO residence FAQs by cohort, ARRO regulations and key dates, Finance Office fee pages, SGS admissions handbook PDFs), but entry points are fragmented and cross-departmental questions must be manually chained. Our differentiation: a single entry point, dynamic tool routing per topic, and every answer labelled with source URL and academic year.

### Database Design Highlights (mapped to Track 1 criteria)

- Tables: `documents` (unique url, title, source, topic, academic_year, crawled_at), `chunks` (chunk_id, doc_id, text, embedding), `crawl_runs` (idempotency/incremental audit), `qa_logs` (questions and citations).
- Normalization: metadata in 3NF; vectors stored via an extension (e.g. sqlite-vec) or a separate ANN index so the relational design stays clean.
- Indexing: B-tree indexes on URL, (topic, academic_year), crawled_at; HNSW index on the vector column.
- Sample queries: (1) list 2025/26 non-local tuition documents and order them by structural fields; (2) semantic search "how long does the student visa take and what documents are required", returning top-k chunks with source URLs.
